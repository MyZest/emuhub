## 问题与原因
- `web/pages/api/devices/[id]/start.js` 使用 `await` 等待脚本完成，接口在系统镜像缺失时会被 `sdkmanager` 安装阶段长时间阻塞。
- 脚本会在前期同步检查/安装系统镜像，随后以 `nohup` 方式后台启动各服务并在日志目录写入日志。

## 优化目标
- 接口快速返回，触发启动流程即可，不等待脚本结束。
- 返回基础信息（设备 id、计算的端口、状态 starting），后续在日志页面通过“刷新”查看进度。

## 后端改动
- 修改 `start.js`：将脚本调用改为非阻塞后台启动。
  - 使用 `execa(..., { detached: true, stdio: 'ignore' })` 或 `child_process.spawn` 启动 `/opt/tools/start-device-session.sh` 并 `unref()`，立即返回。
  - 参数保持不变：`DID DISPLAY VNC_PORT WS_PORT VNC_PASS PROFILE API`。
  - 响应：`{ ok: true, device: { id: did, api, profile, vnc: vncPort, ws: wsPort, status: 'starting' } }`。
- 可选增强：将脚本标准输出也追加到 `session.log`（便于查看最终选定端口的 JSON），实现为 `bash -lc "/opt/tools/start-device-session.sh ... >> /var/log/emuhub/d${id}/session.log 2>&1"` 的后台执行。

## 前端配合
- 现有页面已在 Start 成功后跳转至 `/devices/${id}?tab=logs`，用户手动点击“Refresh”即可看到最新日志与端口调整信息（若发生冲突会在 `session.log` 写入“picked”记录）。
- 如需保留 noVNC 立即打开，可在日志页提供“打开 VNC”按钮，使用接口返回的计算端口；若端口被调整，用户刷新后即可看到正确端口。

## 验证方案
- 场景一：系统镜像已安装 → 接口立即返回，日志页能看到各服务启动日志。
- 场景二：系统镜像未安装 → 接口立即返回，`session.log` 及 `emulator.log` 随时间更新，刷新可见安装与启动进度。
- 场景三：端口占用 → `session.log` 记录 picked 端口；刷新后显示新端口。

## 变更范围
- 仅修改 `web/pages/api/devices/[id]/start.js` 的脚本调用方式为非阻塞；其余逻辑与参数校验保持不变。
